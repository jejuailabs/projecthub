# 01. 제품 정의와 가치 검증

## 대상과 문제

주 사용자는 여러 프로젝트를 병행하는 기획자/PM, 프리랜서, 1인 제작자다. 개발자도 포함하되 개발 저장소가 있어야만 유용한 제품으로 만들지 않는다. 팀 협업 계정 기능은 P1이며 P0는 개인이 자신이 참여하는 프로젝트를 모아 보는 제품이다.

회의록·기획서·디자인·개발 이슈·배포 결과가 여러 도구에 분산되면 이름이 달라지고 진행 단계마다 확인할 위치도 바뀐다. Hub가 답할 질문은 '무엇을 하고 있나, 어느 단계인가, 누가 맡나, 다음에 무엇을 확인하나, 무엇이 막혔나, 원본은 어디인가'다.

## 가치 제안

프로젝트마다 여러 원본을 연결하고, 판단에 필요한 최소 업무 필드와 그 출처를 보여준다. 텍스트에서 초안을 만드는 기능은 초기 등록 비용을 낮추고, 기준 도구의 선택적 동기화는 반복 입력을 줄인다. 성공 기준은 카드 수나 연결 서비스 수가 아니라 상황 파악 시간과 관리 부담 감소다.

Zero-maintenance는 지향점이다. 사용자의 연결 범위/매핑 설정, 추출 검토, 충돌 해결까지 없어지는 것으로 설명하지 않는다. 최신 커밋을 '정상 진행', 오래된 문서를 '프로젝트 중단'으로 간주하지 않는다.

## MVP 계약

범위는 [ORCHESTRATION](../ORCHESTRATION.md)의 P0-01~12다. 검색/필터/정렬, 기본 이력, 회의록 생성과 Notion 동기화를 포함한다. 즐겨찾기·태그·팀 초대·테마 프리셋·일반 AI 추천은 포함하지 않는다.

업무 모델은 [11](11-planner-workflow.md)을 따른다. 상태 5개와 단계 8개를 분리하며 담당자, 다음 행동 한 개, 목표일, 대기/차단 사유를 둔다. 채우지 않은 값은 추측하지 않는다. 진행률 %와 복잡한 태스크 계층은 제공하지 않는다.

## 대표 사용 예

회의록에서 출시 캠페인 후보를 추출하고 검토해 생성한다. Notion의 기획 페이지와 Figma URL을 연결한다. 담당자·승인 대기·목표일을 확인하고 원본에서 승인 요청을 처리한다. 개발이 포함되면 GitHub/Vercel을 추가한다. 프로젝트 화면은 같은 자리를 유지하고 단계와 근거만 바뀐다. 배포 없는 캠페인도 종료할 수 있다.

## 파일럿과 판정

다음 수치는 검증 목표이며 이미 달성한 사실이 아니다. 기획자 5명 이상, 각 실제 프로젝트 3~5개, 2주 사용을 기준으로 시작한다.

| 지표 | 측정 | 초기 성공 목표 |
| --- | --- | --- |
| 상황 파악 시간 | 같은 3개 프로젝트의 단계/다음 행동/원본을 찾는 전후 과제의 중앙값 | 기존 대비 50% 감소 |
| 재진입 시간 | 대시보드 진입부터 올바른 원본 열기까지 | 중앙값 30초 이내 |
| 추가 관리 부담 | 매주 Hub만을 위해 입력/정리한 시간 | 사용자당 10분 이하 |
| 반복 사용 | 둘째 주 서로 다른 3일 이상 핵심 행동 | 참여자의 60% 이상 |
| 정보 신뢰 | 표본 핵심 필드를 원본과 대조 | 95% 이상 일치; 오래된 값은 반드시 표시 |
| 잘못된 동작 | 동의 없는 쓰기·조용한 충돌 덮어쓰기·중복 페이지 | 관측 0건 |

첫날 활성화는 프로젝트 3개 등록, 원본 연결 1개, 다음 행동 확인 1회로 측정한다. 주의 항목을 실제로 해결했는지와 원본 복귀 성공 여부를 관찰한다. 자동 연동 없는 사용자도 별도 표본으로 확인한다.

실패 사유는 누락, 잘못 연결, 단계 불일치, 오래된 정보, 다음 행동 없음, 원본 찾기 실패, 반복 입력 부담으로 기록한다. 이름·회의 원문·외부 URL을 분석 이벤트에 넣지 않는다. 기술 출시 판정과 제품 가치 검증 결과를 별도로 보고한다. 목표 미달이면 서비스 수 확대보다 원인 필드와 흐름을 먼저 보완한다.
